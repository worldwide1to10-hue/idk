## What the research supports

Your top layer planning and a lower layer executing is the orchestrator-worker pattern. Anthropic's version used Opus as lead with Sonnet subagents and beat a single Opus agent by 90.2% on an internal research eval, while using roughly 15× the tokens of chat. Their own conclusion is that much of the gain comes from spending more tokens in parallel, not from the structure itself.

NVIDIA's research group makes your cost argument formally. They argue agent systems should be built from small models by default, with large models called only on demand. Your context-pollution argument is also the main reason Claude Code subagents exist. Each one runs in its own context window and returns only a summary to the parent.

## Where you're probably wrong

**1. Multi-agent often hurts.** Google's study of 180 configurations found that parallelizable tasks gained up to 81%, while on strictly sequential tasks every multi-agent variant lost 39–70%. Gains also shrink once a single agent already scores above roughly 45%, and tool-heavy tasks suffer because the token budget gets split across agents. Anthropic admits that coding tasks where all agents need the same context are poorly suited to current multi-agent systems. Your first design question should be whether to split at all, before how many agents or which topology.

**2. Cheap models don't just "execute exactly."** The Berkeley failure study (MAST) found 14 failure modes in three groups: specification problems, inter-agent misalignment, and weak task verification. Verification is the part your design is missing. Google measured that independent agents amplify errors 17.2×, while an orchestrator that checks outputs holds it to 4.4×. Your pyramid needs a verifier step, ideally deterministic (tests, schema validation), and it should not fall to the planner's context.

**3. The escalation direction.** Research on cascades like FrugalGPT lets a cheap model run the task and call a stronger model only when stuck. Anthropic now ships this as an advisor tool, where a cheaper executor consults an Opus advisor mid-task. You should keep top-down planning for decomposition, but execution should escalate bottom-up. Otherwise your expensive model pays for every step of supervision.

**Speculation:** Here the literature contradicts you. Speculative systems use a cheap model to predict steps and the strong model to verify.         return True
