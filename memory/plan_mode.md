# Pyramid Implementation Plan v3

Updated: 2026-11-12. This is the active roadmap for a highly capable personal coding agent. Research claims inform experiments; they are not workload-specific guarantees or fixed acceptance thresholds.

## Goal

Build the most capable useful provider-agnostic pyramid for one user's local agent: an intelligent L1 planner, isolated and adaptive L2 workers, and deterministic L3 tools and reusable workflows. Optimize first for task quality, context focus, reliability, and useful latency. Available compute and API capacity may be spent when they materially improve those goals; track tokens, calls, latency, and provider limits, but do not treat token minimization as the objective. Keep a strong single-agent path as the baseline and fallback; a negative fan-out result must not cancel useful verification, tools, or context improvements.

## Architecture Decisions

- **L1 owns the global plan.** With the full task context, it emits a DAG of contracts, dependencies, ownership boundaries, assumptions, and join criteria. Do not add a separate divider model. L1 may inspect results and revise the plan.
- **L2 workers are isolated adaptive executors.** Each gets a fresh context, a configured model, an explicit task contract, bounded budgets, and only its granted tools. The worker may plan local steps and recover locally inside that contract; there is no separate divider model. It cannot widen its scope or edit the global plan. If evidence reveals a deeper question or a new independent branch, it returns a typed expansion request to L1; L1 decides whether to deepen that node or add a bounded sub-DAG. Recursion is parent-controlled, not an unrestricted child-spawning loop.
- **L3 is deterministic.** Permissions, scheduling, leases, budgets, schemas, verification checks, persistence, and workflow execution are code, not shared model memory.
- **Choose execution mode per node.** Keep a single-agent path for sequential, tightly coupled, small, or tool-heavy work. A node may execute alone, fan out over independent siblings, or request deeper exploration when evidence changes what is known. Wide fan-out handles coverage; parent-mediated recursion handles depth and replanning. These modes compose in one DAG rather than selecting one topology for the whole run. Begin with parent-authorized expansion and a depth cap of two; reconsider the cap only after the integrated evaluation.
- **Choose execution mode for capability, not token thrift.** The current gate (sequential or <=8 estimated steps stays single; wide needs at least 3 branches plus read-heavy work or disjoint writes) is a conservative eligibility filter, not an optimizer. Split when context isolation, independent expertise, coverage, or wall-clock parallelism is likely to improve the result enough to justify added orchestration. Account for planning, join, verification, provider queueing, calls, and tokens; accept extra resource use when it buys useful quality or capability. Do not hard-code paper-derived thresholds or treat the current gate as evidence that fan-out helps.
- **Bound concurrency and ownership.** Begin with the existing maximum of 8 DAG nodes and 4 concurrent tasks. Declare exact file scopes. The scheduler may overlap disjoint writers only after rejecting unordered write/write and read/write overlaps; dependencies serialize declared read-after-write work. Declared-file staging, optimistic workspace conflict checks, detached Git worktrees for writable nodes in Git-root projects, and a per-node file-commit journal are implemented. `TaskSpec` now supports one explicit integrator role; when declared, it must depend on every writer, own a disjoint output scope, and is checked before execution. Keep multi-file code DAGs opt-in until crash/partial-write recovery is exercised and the integrated code workflow is calibrated.
- **Route from task and trajectory state.** Keep the complexity-to-tier mapping configurable (already present), then let deterministic policy consider the contract, current step, dependencies, budget remaining, validation failures, and prior attempts. This can be a control-plane function; it need not add a model call before every dispatch. Escalate to a stronger model on typed evidence such as invalid output, failed acceptance, verifier rejection, loop detection, or exhausted tool-error budget. Consider learned routing only after telemetry is sufficient to compare it against fixed-tier baselines. Keep model IDs in configuration and log actual IDs per attempt.
- **Use a local blackboard, not agent chat.** Workers communicate through declared dependencies, validated outputs, artifact references, and lifecycle events, not free-form peer chat. SQLite plus an in-process queue is the right coordination mechanism for this single-process personal agent. Persist versioned task events, contracts, summaries, and artifact references. Redis Streams is a possible future transport only if workers become multi-process; Redis Pub/Sub is not a durable control log.
- **Keep workflows distinct from schemas.** JSON Schema/Pydantic describes inputs and outputs; it does not turn a tool-call sequence into a safe executable workflow. A reusable workflow needs a versioned implementation, capability/permission manifest, input/output schemas, tests, provenance, and explicit promotion. New workflows remain quarantined and user-approved.
- **Delay speculation.** If evaluated later, a cheap proposer may start only read-only, cancellable work. Its result is provisional and cannot commit or influence writes until checked by the authoritative worker/planner.

The exact benefit of multi-agent systems, model routing, verifier depth, and spawn thresholds is task- and model-dependent. Treat figures from papers and vendor evaluations as hypotheses. Prefer matched local measurements and preserve useful single-agent improvements even if wide execution is not worthwhile for a task class.

The pasted research summaries in `memory/copy.txt`, `memory/pasted _text #2`, and `memory/pasted_text # 1` are idea generators, not a validated specification. Transfer the qualitative lessons (parallelize independent work, isolate contexts, use explicit contracts, verify outputs, escalate on evidence, and quarantine generated workflows); do not copy headline percentages, fixed agent counts, or named mechanisms without checking the primary source and its task setting. A schema registry describes and versions contracts; it is not itself the authorization boundary, which remains enforced by runtime tool grants. A final integrated evaluation may show a quality or capability gain even when tokens increase; report that tradeoff rather than calling it a failure by default.

## Implementation Sequence

Complete and validate implementation phases first, using offline tests and mocked providers continuously. Defer live benchmark spending until the final calibration gate below. Keep wide execution opt-in; do not make it the default globally. If the final benchmark shows no repeatable benefit for a task class, retain useful contracts, routing, verification, and tools while keeping fan-out experimental.

### Phase 1: Pyramid Contracts And Evidence Path

1. **Make the contracts executable end to end.** Versioned Task, lifecycle, result, and artifact models are validated; Task contracts carry assumptions and join criteria, and worker failure/escalation/contract-change responses are runtime outcomes. Continue to version verifier verdicts and add structured resource ownership for non-file resources when a real task requires it.
2. **Make the evaluation gate trustworthy.** Require the intended baseline matrix and telemetry in the validator. Add explicit checks that a gate-eligible case actually launched workers. Keep “not measured” distinct from zero.
3. **Broaden deterministic acceptance safely.** Confined file assertions, file JSON Schema checks, structured-output assertions, and structured-output schema checks are implemented. Add any further non-arbitrary checks needed by real tasks, and improve coding cases so file presence alone cannot masquerade as behavioral correctness. Keep arbitrary commands disabled until an OS sandbox exists.
4. **Complete local run records.** Task run specs, outcomes, recovery links, and budget usage persist in SQLite and restore by `run_id`; lifecycle events and progress snapshots are versioned. Inspection and explicit reviewed reconciliation exist; automatic replay is rejected. Add a persisted-run cancellation action and document partial-write handling. Keep crash recovery useful for this personal single-process runtime; do not build multi-user event infrastructure.
5. **Persist artifacts by content identity.** Worker artifacts are copied to a private SHA-256-addressed local store with size and workspace-path references. Reads verify the content hash, and garbage collection lists unreferenced blobs by default and deletes only when explicitly requested. Keep full bytes out of L1 context.
6. **Measure budgets and routing.** Retain configurable complexity tiers; record input/output tokens, model calls, provider attempts, tool errors, and time. Aggregate caps reserve declared per-node ceilings and reconcile measured usage. Exercise RPM/TPM admission against observed usage and keep conservative headroom because token estimates are approximate.

**Exit:** malformed contracts and failed deterministic checks cannot reach dependents; report validation rejects missing matrix/telemetry; structured outputs survive parent and dependency boundaries; local events and artifact references survive restart; budget accounting is observable.

### Phase 2: Verification, Adaptive Routing, And Recovery

1. **Harden the existing opt-in verifier.** Offline tests cover malformed verdicts, rejection, timeout, provider unavailability, and candidate-content injection. Keep it opt-in until the final integrated live evaluation measures false accepts/rejects on representative tasks.
2. **Verify joins.** Declared dependency output schemas, combined dependency-map schemas, and equality checks across dependency paths are enforced before a join worker starts. Add frozen-interface or richer semantic checks where real multi-artifact tasks demonstrate the need.
3. **Add bottom-up automatic escalation.** One explicit `needs_escalation` response retries at the next distinct configured tier within remaining node budgets; attempts and combined usage are reported. Next, consider a separate advisor consultation only for unresolved typed evidence, with the same shared attempt limits. Never automatically apply a contract-change request.
4. **Extend bounded evidence-driven re-decomposition.** L1 can reload runs, recover failed leaves across multiple bounded runs, and inspect/reconcile interrupted progress after side-effect review. Unresolved failed/escalation leaves can be retried as one-node recovery tasks within the original scope. Offline tests cover recovery-depth exhaustion, corrupt commit manifests, cancellation, and partial writes. Keep depth capped at 2 initially; workers request expansion and the coordinator validates it, rather than receiving unrestricted recursive-spawn tools.
5. **Harden code-writing DAGs.** The scheduler rejects unordered read/write or write/write overlaps and stages declared file outputs, committing only successful results after optimistic version checks. Writable nodes in Git-root projects use detached worktrees, and an explicit integrator role is available with validated writer dependencies and disjoint output scope. Exercise the file-commit journal under crash and partial-write cases, then calibrate integrator workflows before broadening multi-file code DAGs.

**Exit:** invalid, rejected, or inconsistent results are blocked; escalation is bounded and observable; cancellation leaves no untracked writes; verifier quality is measured; sequential controls remain single-agent.

### Phase 3: Reusable Workflows And Tools

An initial versioned workflow manifest and registry support declarative `Read` steps and offline `Bash` steps inside bubblewrap. Bash receives only a copied, read-only snapshot of declared non-credential project files, has no network access, and is bounded by CPU time, process count, open files, temporary storage, per-file size, and output limits. Workflows have input/output schemas, test cases, session quarantine, successful-use telemetry, promotion-readiness suggestions, and explicit owner approval. Write-capable or nested workflows still require stronger isolation. Keep provenance and versions pinned, and never allow self-promotion or infer executable semantics from JSON Schema alone.

**Exit:** a candidate passes isolated tests, is reused successfully across distinct tasks, stays within declared capabilities, and is explicitly approved. Otherwise keep it session-scoped or discard it.

### Phase 4: Learned Routing And Speculation

Use stable, labeled telemetry to compare adaptive or learned routing with fixed-tier baselines. A cheap proposer is one candidate, not an assumption; route stronger models to uncertain or high-impact work when that improves outcomes. Limit speculation to read-only, cancellable work; do not let provisional results commit writes or become authoritative before verification. Keep data-dependent routing and speculation disabled until the final held-out evaluation. Run ablations for routing, fan-out, verifier, recovery, and speculation so their contribution is identifiable.

**Exit:** every added mechanism shows repeatable quality-preserving improvement on held-out personal workloads. Retain advanced capabilities that improve capability or reliability even if they do not reduce tokens; remove or disable mechanisms whose cost is not justified by measured value.

### Final Phase: Live Calibration And Promotion

1. After implementation phases are complete, run one integrated live evaluation campaign with fixed model IDs, the designated region aggregation case, representative personal coding tasks, and sequential, tightly coupled, exploratory, research, data, and tool-heavy controls. Use the full target task set for promotion; smaller reports are pilots only. Do not spend live benchmark calls during implementation; use offline tests and mock providers for incremental validation.
2. Within that campaign, compare single-T2, single-T3, and the complete pyramid, plus feature ablations for fan-out, routing/escalation, verification, recovery, workflows, and speculation. Separate any tuning/development tasks from a held-out evaluation set so the same results are not used to tune and claim improvement.
3. Verify actual child calls, worker/model IDs, attempts, lifecycle events, total input and output tokens, latency, failures, verification outcomes, workflow reuse, and human review across task shapes. The earlier summary without child telemetry is not sufficient evidence.
4. Report paired per-task and per-shape outcomes, including quality/capability gains that cost more resources. If a candidate was marked wide-eligible but did not launch workers, fix the harness/prompt and rerun that case; do not call it a negative parallel result. Enable modes by task class only after the integrated results support them.

**Exit:** a complete, telemetry-valid matched report with review coverage and clear per-class decisions. Price is optional; unknown cost stays null. No live benchmark is a prerequisite for the implementation phases above.

## Personal-Agent Safety Boundary

Do retain strict worker tool scopes, explicit user approval for promotion, cancellation and budget limits, and the distinction between application checks and OS isolation. Do not expose Bash or generated executable tools to workers until OS-level sandboxing and secret isolation exist.
